> 配套 spec：[../docs/spec.md](../docs/spec.md)

## 实现策略

采用"地基先行 → 后端垂直切片 → 前端切片 → 联调"的混合策略。纯垂直切片每任务都要碰前后端会让任务过大，所以后端先按数据层→能力层→graph核心→流式报告切片，前端按页面切片，最后联调。

## 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| Spring AI Alibaba graph API 不熟悉 | 高 | 高 | T8 前先写最小 demo 验证节点定义/状态传递；T8-T9 是最高风险任务，留充足时间 |
| OpenAI 兼容 API 动态切换 ChatClient | 中 | 高 | T8 用 `OpenAiChatModel` 工厂模式，按 model_config 实时构造，不依赖 Spring AI 的自动配置 bean |
| SSE + graph 集成（graph 同步执行 vs SSE 异步推流） | 中 | 高 | T11 明确：graph 在独立线程跑，节点产出通过 `SseEmitter.send` 推流；状态用 `BlockingQueue` 或 graph 内置回调 |
| Tika 解析 Word/中文 PDF 乱码 | 中 | 中 | T7 用 Tika `AutoDetectParser` + `BodyContentHandler`，限制 maxStringLength；测试覆盖中英混排 PDF |
| 题库 JSON schema 设计不当 | 中 | 中 | T7 题库上传前先定 JSON schema（type/difficulty/content/standard_answer/scoring_points），写到 spec 附录 |
| 前端 SSE 跨域 + EventSource 不支持 POST | 中 | 中 | T11 后端用 `SseEmitter`，前端用 `EventSource`（GET）或 fetch streaming；CORS 在 T1 配置好 |

## 并行 vs 串行

**可并行：**
- T1（后端骨架）‖ T2（前端骨架）
- T5（模型配置）‖ T6（Skill 加载）‖ T7（文件上传）—— 都只依赖 T4
- T13（设置页）‖ T14（上传页）‖ T15（面试页）—— 前端页面独立
- T16（报告页）依赖 T15 的 SSE store，但可与 T13/T14 并行

**必须串行：**
- T3 → T4 → (T5/T6/T7) → T8 → T9 → T10 → T11 → T12
- 任何后端 API 必须先于对应前端页面

| CP6 | T16 后 | 前端四个页面都能正常渲染，能调通后端 |
| CP7 | T17 后 | spec 的 10 条 Success Criteria 全部满足 |

## 任务大小约束

- 每个任务触碰文件 ≤ 5 个（schema/entity 批量生成任务除外）
- 每个任务单 session 可完成
- 每个任务有明确验收 + 验证步骤
